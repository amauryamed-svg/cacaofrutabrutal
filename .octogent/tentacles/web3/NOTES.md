Format: `YYYY-MM-DD — Decision — One-line rationale.`

## 2026-04-27 — Phase 7 code-side ship

- 2026-04-27 — `LPTimelock` is single-position by design. One LP NFT per timelock instance — if the next 12-month rollover wants different parameters (e.g. concentrated range), we deploy a fresh timelock. Trade-off: more contracts deployed over time, but each is auditable individually and the prior lock can't be silently expanded.
- 2026-04-27 — `LPTimelock.collectFees` does NOT include `decreaseLiquidity`. The contract only exposes `collect` from the NPM, which pulls accumulated trading fees without burning principal. Adding `decreaseLiquidity` would be an explicit policy change requiring a new contract deploy.
- 2026-04-27 — `LPTimelock.onERC721Received` rejects deposits from any contract other than the configured NPM. Reason: defense in depth against accidental sends of unrelated NFTs (which would otherwise be retrievable via admin path — but we have no admin rescue here). Cleaner model: the timelock holds one specific kind of NFT, others bounce.
- 2026-04-27 — `CharterRegistry` has zero admin. No pause, no removal of signatures, no upgrade path. Reason: Charter principle I.5 (Transparencia radical) — once a signature is recorded, it must be permanent. If we ever want to "delete" a sig, we deploy a new registry; the old one keeps its history.
- 2026-04-27 — `CharterRegistry.sign` is open to anyone — not just founders. Reason: Charter §IV (mecanismo de enmienda) calls for quorum of holders representing ≥30% of $CACAO post-Phase 7. Open signing lets any holder ratify a Charter version cheaply. Off-chain UI filters which signers it considers "official" based on role.
- 2026-04-27 — `Deploy.s.sol` Phase 7 deploys are split into `deployLPTimelock()` + `deployCharterRegistry()`. Reason: each is independently runnable; if audit blocks LP seed, CharterRegistry can still launch.
- 2026-04-27 — `scripts/seed_uniswap_v3.ts` uses `safeTransferFrom` to send the LP NFT into LPTimelock. The timelock's `onERC721Received` accepts. Trade-off: a regular `transferFrom` would also work but would skip the `Deposited` event emission — `safeTransferFrom` makes the transfer auditable on BaseScan via the event log.
- 2026-04-27 — `scripts/sign_charter_onchain.ts` parses Charter version from frontmatter (`Versión 1.0` regex). If the Charter format changes, the script breaks loudly. Acceptable tradeoff vs over-engineered TOML parsing.
- 2026-04-27 — `docs/AUDIT.md` lists 5 "known limitations" that are design choices, not bugs. This pre-empts auditor noise on items we have already chosen to live with (e.g. mint-tree-nft decoupled from TreeAdoption). Saves audit time + budget.
- 2026-04-27 — `docs/LAUNCH.md` includes 4-hour public statement SLA on Critical pause. Reason: in Web3, silence after a pause looks like a rug. We commit publicly to communicate within 4h even if we don't have a fix yet.

## 2026-04-27 — Phase 6 code-side ship

- 2026-04-27 — Hash chain decisions: leaves use SHA-256 (matches Ed25519 signing primitive on-device + Python `hashlib`), tree internal nodes use keccak256 (matches Solidity `MerkleProof.verify`). The contract verifies `keccak256(min || max)` per OZ convention. Trade-off: two hash functions in one pipeline. Documented inline in `iot_merkle.py` so future maintainers don't "fix" it.
- 2026-04-27 — Canonical JSON spec: keys sorted alphabetically, no whitespace, UTF-8. Identical encoding produced in three places: `firmware/cacao_node/main.cpp::buildCanonicalJson`, `api/iot_verify.py::canonical_json`, and (implicitly) the receiver. Drift = signature fail. Listed as a top-of-mind invariant in `firmware/cacao_node/README.md`.
- 2026-04-27 — Week index = `floor(unix_ts / 604800)`. Stable across DST, monotonic, identical in PG (`compute_week_index`), Python (`iot_verify.week_index`), and TS (`iotWeekIndex`). Replicated in 3 places by design — single source-of-truth would require importing across language runtimes which we don't have.
- 2026-04-27 — Replay protection: `(device_id, reading_nonce)` unique index in DB + per-reading 16-byte random nonce on device. The on-chain layer doesn't see individual readings (only the root) so all replay defense lives off-chain.
- 2026-04-27 — Receiver auth changed from shared-secret (`X-IoT-Secret`) to per-device Ed25519 signature. Old `iot_readings` table left untouched for backward compat; new readings flow into `iot_readings_signed`. ml_predictor.py reads from the signed table only (rows are signature-verified).
- 2026-04-27 — Weekly cron pattern: pg_cron triggers `net.http_post` to `post-iot-root` Edge Function with `Bearer ADMIN_BEARER_TOKEN`. The Edge Function: queries leaves → computes root → upserts audit row → sends tx via oracle EOA → updates row. Idempotent on (week_index, contract). If the cron fires twice in same week, the second call is a no-op.
- 2026-04-27 — `IoTAttestation` is intentionally upgrade-less. Charter principle I.5 (Transparencia radical) — if leaf format or hash scheme must change, deploy a new contract; old roots stay queryable forever. Loss of writability per week is acceptable given the cost of upgradeability is opacity.
- 2026-04-27 — `latestWeek` only advances; out-of-order back-posts (admin backfill) don't regress it. Verified by `test_PostRoot_DoesNotRegressLatestWeek`. Frontend can read `latestWeek` to show "Last attestation: week N".
- 2026-04-27 — Firmware `secretKey` lives in NVS Preferences. First-boot auto-generation chosen over factory-provisioning. Trade-off: easier ops, but a stolen pre-flashed device with no DEVICE_ID rev pre-registered is harmless (its first POST is rejected with `device_not_registered`). Founder must register the printed pubkey via dashboard before readings start landing.
- 2026-04-27 — `bytea` payload_hash storage: stored as PG bytea, normalised to `0x`-prefix lowercase hex when read by `post-iot-root`. Avoids ambiguity vs `text` (would invite unicode/encoding bugs).

## 2026-04-27 — Phase 5 code-side ship

- 2026-04-27 — `TreeAdoption.sol` does NOT mint the NFT atomically. Decision: NFT mint stays in the existing `mint-tree-nft` Edge Function path. Adoption tx just splits payment + emits `TreeAdopted`. Reason: keep KYC + rate-limit + Paymaster gas accounting in one place (the relayer Edge Function). Atomic minting from `TreeAdoption` would couple two concerns and require granting MINTER_ROLE on the NFT contract to TreeAdoption, expanding audit scope. Trade-off accepted: a buyer who pays via the contract directly without going through the app could pay successfully but never mint. Mitigation: app is the only documented path; if such a stranded payment shows up, support refunds via `rescue()` (admin-only, paused).
- 2026-04-27 — Splits hardcoded as constants (`GUARDIAN_BPS=6000`, `TREASURY_BPS=3000`, `PROTOCOL_BPS=1000`). Deliberately NOT mutable — Charter principle I.1 enforced at bytecode level. To change splits we must deploy a new contract.
- 2026-04-27 — Protocol gets `amount - guardianAmt - treasuryAmt` (residual) rather than its bps share. Reason: integer math rounding. Without this, 1-3 wei dust per adoption would be stuck in the contract forever. Now total received always equals amount paid (verified by `testFuzz_SplitConservation`).
- 2026-04-27 — `receive()` reverts. ETH must arrive via `adoptWithEth`. Direct sends would otherwise sit stranded with no split path. Documented and tested.
- 2026-04-27 — `rescue(asset, to, amount)` requires `paused()` first. Defense in depth: even an admin EOA can't sweep funds during normal operation; multisig must explicitly pause first, which leaves a public on-chain trail.
- 2026-04-27 — Guardian wallet lookup is on-chain (`guardianWallets[guardianId]`), not from off-chain server. Reason: contract must be self-sufficient to honor Charter principle I.1 — payment to Guardian happens in the same tx, no off-chain dependency. Server-side `guardians` table (migration 031) is for analytics/UI, on-chain mapping is authoritative.
- 2026-04-27 — `coinbase-commerce-webhook` was missing since the investor flow shipped. Phase 5 wires it. Routes by `metadata.kind`: `adoption` → `adoption_charges`; anything else → `investor_charges`. Existing investor flow keeps working unchanged.
- 2026-04-27 — `alchemy-nft-webhook` extended to also flip `adoption_charges.status` when it sees activity on the TreeAdoption contract address. Two contract addresses watched in one webhook config — consolidates Alchemy webhook setup.
- 2026-04-27 — `WalletCheckout.tsx` refactor (manual → wagmi) explicitly deferred. Reason: existing manual flow works for investors today; refactoring it would touch user_profiles + investor_charges + record-investor-transfer simultaneously. Better to ship Phase 5 (new adopt path) first, then refactor WalletCheckout in a clean PR.
- 2026-04-27 — `Web3Landing` reuses standalone vanilla Three.js from `/investor-3d.js` (already deployed). Trade-off: no R3F bundle, but lazy script load + CSP must allow `script-src 'self'`. Already does (existing investor landing uses the same pattern).
- 2026-04-27 — Onramp button uses `pay.coinbase.com/buy/select-asset` URL with `appId` from `VITE_COINBASE_ONRAMP_APP_ID`. Coinbase handles all KYC/AML/card processing — CauaCorp never touches fiat (per docs/LEGAL.md Texas MSA argument). 1-2% fee charged to user, not us.

## 2026-04-27 — Phase 4 code-side ship

- 2026-04-27 — `$CACAO` cap = 21M (Bitcoin homage, NOT equivalence). Documented as such in `CacaoToken.sol`. Cap is symbolic and matches Charter narrative — at current adoption math (5 Guardianes × ~5 mazorca/yr × 1k:1 ratio) we use a tiny fraction of the cap; we leave headroom for game-economy scaling.
- 2026-04-27 — `CacaoToken` constructor does NOT grant `MINTER_ROLE` to the deployer. Reason: enforce Charter I.3 (no founder mint outside gameplay) at the bytecode level. Deploy script grants `MINTER_ROLE` only to the `MazorcaRedemption` contract address. Even an admin EOA cannot mint after deploy.
- 2026-04-27 — Redemption flow chosen: server decrements `mazorcas_balance` BEFORE signing the EIP-712 payload. If user fails to claim before deadline, `expire_mazorca_redemptions` cron flips status, then `refund-expired-redemption` Edge Function refunds atomically. Trade-off: better UX (no on-chain pre-flight check needed) at the cost of a refund cron path. Idempotency in refund flow is enforced via `refunded_at IS NULL` check.
- 2026-04-27 — On-chain user cooldown = 30 days; server-side cooldown = 30 days. Defense in depth: even if server logic has a bug, contract enforces. Gas cost of cooldown check is ~2.5k gas per claim — acceptable.
- 2026-04-27 — Rate of 1000 mazorcas → 1 $CACAO is configurable on-chain via `setMazorcasPerToken` (admin role). Server reads from `MAZORCAS_PER_TOKEN` env. Mismatch between server and on-chain rate would cause silent over/under-mint — Phase 4 deploy checklist includes a sanity check post-deploy: server env must match `redemption.mazorcasPerToken()`.
- 2026-04-27 — EIP-712 `claim(data, sig)` requires `msg.sender == data.user`. Reason: prevents random caller from spending another user's signed payload (even though sig already binds to user, requiring caller-equals-user makes blockchain-explorer attribution clean).
- 2026-04-27 — `mazorca_count % mazorcasPerToken == 0` validation lives in the server (not the contract). Reason: contract uses integer division so dust just gets rounded; if we move enforcement on-chain we'd need a `revert WastedDust` and another revert path. Server-side is clearer for the user (modal won't even let you pick fractional values).
- 2026-04-27 — Mazorca burn ledger uses event_type `mazorca_redemption_burn` (negative mazorcas) and `mazorca_redemption_refund` (positive). These are NEW event types not in `award-tokens` TOKEN_RATES — they bypass that Edge Function entirely (sign-mazorca-burn writes directly with service_role). Token economy tentacle owners should be aware.

## 2026-04-27 — Phase 2-3 code-side ship

- 2026-04-27 — Discovered SPA basename = `/app` (line 82 of `src/App.tsx`). Earlier memory note saying "basename actual = `/`" was wrong — corrected. All Web3 routes ship as `/app/web3/*`.
- 2026-04-27 — `AuthContext` exposes `userId` (UUID) + `user` (display name string). New hooks must read `userId`, not `user`. Updated `useKYCStatus` accordingly.
- 2026-04-27 — `cacao_trees.guardian_id` is `int 0..4` per migration 005. NFT `mintTree(uint8 guardianId)` validates `<=4` on-chain. Off-chain enforcement also in `mint-tree-nft` Edge Function.
- 2026-04-27 — Variety hash strategy: `keccak256(toHex(variety))` where variety ∈ {Criollo, Trinitario, Forastero, Nacional}. Stored on-chain as bytes32; decode to string in `tree-metadata` for display. Avoids stuffing full strings into contract storage.
- 2026-04-27 — GPS hash strategy: `keccak256(lat || lng || guardian_salt || PRIVACY_SALT)`. Coords never on-chain; founders read raw coords from `cacao_trees` via RLS. Hash proves correspondence without doxxing the Guardián's exact farm.
- 2026-04-27 — Mint relayer pattern uses **server EOA + viem `sendTransaction`** for MVP. Coinbase CDP Paymaster integration is documented as a TODO in `mint-tree-nft/index.ts` — drop-in upgrade once `CDP_PAYMASTER_URL` + `CDP_API_KEY` are configured. Trade-off accepted: until then, the relayer EOA pays gas (~$0.002/mint on Base, capped at 1 mint/user/24h).
- 2026-04-27 — Mint audit table `tree_mints` separate from `cacao_trees`. Reason: keep `cacao_trees` as game-state source-of-truth (one row per tree). Mint attempts (failed/pending/confirmed) go to a dedicated audit log so retries don't pollute the canonical row. Status flips `pending → submitted → confirmed` via `alchemy-nft-webhook`.
- 2026-04-27 — `tree-metadata` cache headers: `max-age=60, stale-while-revalidate=300`. Reason: OpenSea/Zora poll metadata aggressively; 60s cache reduces Edge Function load while keeping refresh latency acceptable. ERC-4906 `MetadataUpdate` events still trigger immediate refresh on marketplaces that listen.
- 2026-04-27 — `getMetadataAttributes()` lives in `src/utils/growthSystem.ts` and is mirrored (not imported) in `supabase/functions/tree-metadata/index.ts`. Reason: Edge Functions are Deno (no Vite alias), and we want the metadata endpoint to be self-contained. Keep the two in sync; if they drift, marketplace metadata will diverge from in-app UI.
- 2026-04-27 — Stage thresholds (8 stages, 4.6h to maturity) duplicated in tree-metadata. Reason: same as above. Single source-of-truth lives in `growthSystem.ts`; Edge Function gets a static copy. Documented as a maintenance tax in CLAUDE.md §10 followups.
- 2026-04-27 — KYC tier requirements: mint=1, redeem=1, adopt_crypto=2, equity=3. Reason: mint/redeem are utility-grade actions (NFT + utility-token interaction) — Tier 1 ID + country sufficient. Crypto adoption flows actual money → Tier 2 (selfie + address) per FinCEN best-practice for transactions ≥$1k. Equity requires accreditation per Reg D 506(c) — Tier 3.
- 2026-04-27 — Foundry deps not yet installed. `lib/openzeppelin-contracts` and `lib/forge-std` excluded via `.gitignore`. User must run `forge install OpenZeppelin/openzeppelin-contracts@v5.0.2 forge-std` before `forge build` succeeds.
- 2026-04-27 — npm deps not yet installed. New deps in `package.json`: `wagmi@2.14.0`, `viem@2.21.0`, `@rainbow-me/rainbowkit@2.2.4`, `@coinbase/wallet-sdk@4.3.0`, `@tanstack/react-query@5.66.0`, `siwe@3.0.0`. Run `npm install` before `npm run build`.

## 2026-04-27 — Tentacle creation

- 2026-04-27 — Tentáculo `web3` creado como noveno tentáculo. Razón: la transformación on-chain cruza 5+ tentáculos existentes y necesita owner único para evitar drift entre frontend, contratos, Edge Functions, IoT y compliance.
- 2026-04-27 — Chain primaria: **Base** (Coinbase L2 EVM). Razón: gas ~$0.001/tx, RPC gratis CDP, cbBTC nativo, alineado con audiencia Austin/Coinbase. Descartado Polygon (menor mindshare cripto-puro), Optimism (sin cbBTC), Solana (no-EVM, audit doble).
- 2026-04-27 — Token model: `$CACAO` ERC-20 cap 21M earn-only via burn de mazorcas; **NO** presale, **NO** allocation founders fuera de gameplay. Razón: Charter principio I.3 + minimizar exposición Howey/SEC. Liquidez DEX se difiere a Phase 7 post-audit, con LP timelocked 12 meses.
- 2026-04-27 — NFT árbol: ERC-721 con `tokenURI` dinámico (IPFS birth-cert + Supabase Storage game-state). Razón: cada árbol único justifica unicidad ERC-721 vs ERC-1155; mercado secundario requiere transferibilidad. Soulbound descartado porque mata el valor cryptobro.
- 2026-04-27 — Wallet UX: Coinbase Smart Wallet (passkey) primario + RainbowKit fallback. Razón: passkey onboarding para newcomers (Austin tourists, LATAM cacao-lovers); RainbowKit cubre Rabby/MetaMask hardcore. Una integración wagmi v2 sirve a ambos.
- 2026-04-27 — KYC provider: **Persona** hosted flow. Razón: $0 hasta 1k verifs/mes, webhook simple, hosted UI quita responsabilidad UX. Descartados Sumsub (más caro pre-Series A), Veriff (UX más fricción), Coinbase Verifications (acoplamiento prematuro).
- 2026-04-27 — AML: Chainalysis Address Screening free tier + OFAC SDN cron-pulled a Supabase. Razón: combo cubre 99% del threat model de un protocolo agroforestal (no exchange, no DEX core). TRM Labs queda parking lot post-Series A.
- 2026-04-27 — Sync on→off chain: Alchemy webhook → Supabase Edge Function. Razón: 100k events/mo gratis, sin operar Ponder/Goldsky, latencia <60s aceptable para refresh metadata.
- 2026-04-27 — Metadata storage: Pinata IPFS (birth-cert inmutable) + Supabase Storage signed URLs (game-state mutable). Razón: birth-cert necesita inmutabilidad descentralizada (IPFS), game-state cambia diario (Storage cheaper + escalable). Arweave overkill v1.
- 2026-04-27 — IoT attestation: ESP32 + Ed25519 + Merkle root semanal on-chain. Razón: $50/Guardián vs $400 Helium; 1 tx/semana ≈ $0.05; libsodium-arduino disponible; zk-proofs out-of-scope solo-founder.
- 2026-04-27 — Smart contracts: Foundry + OpenZeppelin v5. Razón: Foundry fuzz/invariant tests cubren 80% del valor solo-audit; OZ v5 audited base; comunidad Base usa Foundry de facto.
- 2026-04-27 — Audit deferred a Phase 7. Razón: contratos cambian mucho durante Phases 3–5; auditar antes = re-auditar. Foundry tests + manual review son suficientes para soft-launch interno hasta abrir mercado secundario.
- 2026-04-27 — Web3 routing: ruta `/web3/*` separada de la SPA pública (`/`). Razón: lazy-load wagmi/viem/RainbowKit (~80kb gz) solo cuando necesario, marketing root no paga el bundle cost.
- 2026-04-27 — Compliance program parte de Phase 1 ANTES de Phase 2. Razón: KYC implementation sin política documentada = riesgo regulatorio. `docs/COMPLIANCE.md` + `docs/CHARTER.md` definen el espíritu antes que el código lo aplique.

## 2026-04-27 — Cross-tentacle handshakes acordados

- **token-economy ↔ web3:** beans/mazorcas siguen 100% off-chain. La única bridge es `MazorcaRedemption.sol` (Phase 4) que decrementa `mazorcas_balance` vía EIP-712 firmado por server y mintea `$CACAO`. token-economy no toca cadena directamente.
- **cacao-gotchi ↔ web3:** care actions siguen escribiendo a Supabase. `tree-metadata` Edge Function lee Supabase + emite `ERC-4906 MetadataUpdate` event vía relayer. growthSystem.ts agrega un re-export `getMetadataAttributes(tree)` para `tokenURI` — sin cambio de lógica de juego.
- **ml-pipeline ↔ web3:** `ml_predictor.py` consume `iot_readings_signed` (rows ya verificadas en `iot_verify.py`). Privacy SHA-256 anon_token se mantiene; el cambio es upstream (origen de datos), no en el modelo.
- **supabase-backend ↔ web3:** migrations 028–032 son owned por web3 pero requieren review de supabase-backend (RLS pattern, índices, GIN/BRIN). Sin excepciones a `(select auth.uid())` y `service_role only via Edge Functions`.
- **infra-devops ↔ web3:** Foundry CI corre en GitHub Actions (no Vercel). Alchemy webhook URL en Vercel env. Secrets nuevos (Persona, Pinata, Alchemy, Coinbase CDP) en Supabase config.toml + Vercel env, nunca en repo.
- **design-system ↔ web3:** Web3 components (ConnectWalletButton, MintTreeButton, etc.) heredan BRAND palette (heirloom/amazon/pod/mazorca/criollo/theobroma/bgDeep), brutalist luxury, hex-only. Sin nuevos primitives sin review design-system.
- **b2b-marketplace ↔ web3:** Phase 5 migra `WalletCheckout.tsx` de manual ETH-paste a wagmi `writeContract` a `TreeAdoption.sol`. Manual flow queda fallback solo para usuarios sin Smart Wallet/RainbowKit.
- **blog-cms ↔ web3:** sin dependencia directa Phase 1–7. Phase 7+ podríamos NFT-gate algunos posts ("holders-only Charter ratification") pero parking lot.
